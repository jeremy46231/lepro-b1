# noble adopts LE connections it did not initiate

Report drafted against [`@stoprocent/noble`](https://github.com/stoprocent/noble), for
[issue #97, "onLeConnComplete adopts LE connections noble did not initiate"](https://github.com/stoprocent/noble/issues/97),
which was closed as "invalid as originally evidenced". This is the foreign-connection
capture that issue lacked.

Found while debugging matter.js (`matterjs-server --bluetooth-adapter=0`) breaking every
unrelated BLE device on the same host.

## Summary

On Linux the HCI socket is a broadcast view of the controller, so an `LE Connection
Complete` generated by *another* host stack is delivered to noble too, with `role = 0`.
`onLeConnComplete` adopts it: it builds an `AclStream` and a `Gatt` and calls
`exchangeMtu()`. That puts a second ATT client on a bearer that already has one.

The practical effect is that BlueZ can no longer complete GATT discovery for that peer.
The peripheral connects, `Connected=true` and `ServicesResolved=true` are both reported,
and zero `GattService1` objects are ever exported. Any BlueZ-based client (bleak, and
therefore Home Assistant) sees a connected device with no services, forever.

## Why this is not the case retracted in #97

#97 was withdrawn because the capture turned out to show noble's own kernel L2CAP
workaround rather than a genuinely foreign connection. Here the two ATT clients are
plainly two different processes, on the same connection handle, 16ms apart. `btmon`
labels each frame with its owning process:

```
MainThread[1914]:  < ACL Data TX: Handle 21 flags 0x00 dlen 7   #8  [hci0] 2.255791
      ATT: Exchange MTU Request (0x02) len 2
bluetoothd[12032]: < ACL Data TX: Handle 21 flags 0x00 dlen 7   #13 [hci0] 2.271699
      ATT: Exchange MTU Request (0x02) len 2
> ACL Data RX: Handle 21 flags 0x02 dlen 7                      #24 [hci0] 2.302631
      ATT: Exchange MTU Response (0x03) len 2
> ACL Data RX: Handle 21 flags 0x02 dlen 7                      #25 [hci0] 2.302636
      ATT: Exchange MTU Response (0x03) len 2
```

PID 1914 is the matter.js node process. PID 12032 is `bluetoothd`. `bluetoothd` opened
the connection; noble never called `connect()` on this peripheral, and never would have,
since matter.js scans with the Matter `FFF6` service filter and this device is a light
bulb that does not advertise it.

## Reproduce

Any non-Matter BLE peripheral, one adapter managed by BlueZ:

```sh
# with an idle matterjs-server --bluetooth-adapter=0 running
python -c "import asyncio,bleak; ..."   # bleak connect() + get_services()  -> services = 0
systemctl stop matterjs-server
python -c "import asyncio,bleak; ..."   # same script                       -> services = 2
```

Observed on both of two identical bulbs, every attempt, across reboots. Stopping the
node process is sufficient and immediate; nothing else about the system changes.

## Root cause

`lib/hci-socket/bindings.js`, `NobleBindings.prototype.onLeConnComplete`. The only guard
is the role check:

```js
if (role !== 0 && role !== undefined) {
  // not master, ignore
  return;
}
```

Nothing below that establishes that noble initiated the connection. On `status === 0` it
unconditionally constructs the stack and, further down, wires up `Gatt` and exchanges
MTU. `connect()` already records every request in `this._connectionQueue` as
`{ id, address, addressType, params }`, so the information needed to tell the two cases
apart is present.

## Patch

```diff
--- a/lib/hci-socket/bindings.js
+++ b/lib/hci-socket/bindings.js
@@ NobleBindings.prototype.onLeConnComplete = function (
   if (role !== 0 && role !== undefined) {
     // not master, ignore
     return;
   }
 
+  // Only adopt connections this process initiated. On Linux the HCI socket is
+  // a broadcast view of the controller, so a connection opened by BlueZ, or by
+  // any other host stack sharing the adapter, is delivered here as well with
+  // role 0. Adopting it attaches a second ATT client to a bearer that already
+  // has one, and the exchangeMtu() below then races the owning stack's own.
+  if (status === 0) {
+    const id = this.addressToId(address);
+    const initiated = this._connectionQueue.some(
+      (conn) => this.addressToId(conn.address) === id
+    );
+    if (!initiated) {
+      return;
+    }
+  }
+
   let uuid = null;
   let error = null;
```

If adopting foreign links is wanted by some consumers, gating it behind an explicit
option rather than defaulting to on would still fix the shared-adapter case.

## Secondary issue in the same block

When the address is unknown, the synthetic-discovery path does:

```js
this._scanServiceUuids = []; // We have to set this to fake scan
```

That is process-global and never restored, so a single adopted connection silently
discards the caller's service-UUID scan filter for the remainder of the process. With
the patch above this stops being reachable via foreign connections, but it is worth
saving and restoring regardless.

## Environment

| | |

| BlueZ | 5.86 |
| adapter | Qualcomm USB, HCI 4.2 |
| OS | NixOS, kernel 6.x |
| peers | ESP32-based BLE peripherals (Lepro bulbs), no `FFF6` |

## Workarounds

Either removes the conflict without patching noble:

- `NOBLE_BINDINGS=dbus`, making noble an ordinary `org.bluez` client rather than a raw
  HCI socket user. Upstream matterjs-server documents this as the recommended backend.
- For matter.js specifically, `--ble-proxy` instead of `--bluetooth-adapter=N`, which
  leaves the adapter entirely to the other stack.
